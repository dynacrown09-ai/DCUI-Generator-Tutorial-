Step-by-Step Tutorial: Building Your First UI Flow

#

Let's walk through building a complete, real-world Minecraft Bedrock script UI: a Staff Admin Menu opened by right-clicking a compass while crouching.

1

Add and configure a Trigger

  1. In the Element Library (left), click or drag a Trigger node onto the canvas.
  2. Click the Trigger node to open the Properties Panel (right).
  3. Set Event to Crouch + interact with this item — or choose Item used (right-click) and set Crouch rule to Only while crouching (sneaking).
  4. In Item (item used), enter minecraft:compass.
2

Add and connect a Form

  1. From the library, add a Form node.
  2. In the Properties panel set Form type → Modal form (inputs), Title → §l§6Staff Utility Menu, Submit button → Execute Action.
  3. Wire the Trigger to the Form: click or drag from the Trigger's open (out) port to the Form's trigger (in) port.

typescriptscripts/main.ts 
// DYNACROWN Visual Script UI Editor — generated script
import { world, system } from "@minecraft/server";
import { ModalFormData } from "@minecraft/server-ui";

function openForm_staffUtilityMenu(player) {
  const form = new ModalFormData()
    .title("§l§6Staff Utility Menu")
    .toggle("Enable Night Vision", true)
    .slider("Teleport Height (Y)", 64, 320, 10, 100);

  form.show(player).then((res) => {
    if (res.canceled) return;
    const giveVision = res.formValues[0];
    const targetY   = res.formValues[1];

    if (giveVision == true) {
      player.addEffect("night_vision", 300 * 20, { amplifier: 1 });
      player.runCommand(`tp @s ~ ${targetY} ~`);
    }
  });
}

world.afterEvents.itemUse.subscribe((ev) => {
  const player = ev.source;
  if (ev.itemStack?.typeId !== "minecraft:compass") return;
  if (!player.isSneaking) return;            // crouch + item use
  openForm_staffUtilityMenu(player);
});
04

Wiring Engine & Port Rules

#

The visual editor uses a directional port architecture:

Port style / labelColour / appearanceFunction & allowed connections
Flow Output
open, controls, next		 Purple / Cyan Sequences triggers into forms, or chains UI controls together.
Action Output
submit, on click, then		 Emerald green Executes logic when a form is submitted or a button is pressed.
Condition Outputs
yes ✓, no ✗		 Amber / gold Branches execution based on boolean or comparison expressions.

Build your UI in 3 steps

  1. Add a Trigger (e.g. Item used → minecraft:stick, or Crouch + interact with this mob → minecraft:villager) and connect it to a Form.
  2. Chain Controls from the form's controls port — order in the form = order of the chain.
  3. Connect Actions to the form's submit port — they run after the player submits. Buttons: connect actions to the button's on click port instead.

Multi-wire rules

🔀 One-to-many fan-out

Every output port supports multiple simultaneous connections:

  • A single Trigger can trigger multiple forms or log events.
  • A single Action or Submit port can fan out to execute several independent action branches in sequence.

🔢 Badge indicators

Ports with 2 or more active connections display a numerical badge — [2], [3] — so you can see fan-out at a glance without tracing wires.

👆 Tap-connect mode

Tap any output port to enter connection mode (compatible targets glow), then tap target input ports to connect. You can tap multiple targets continuously without re-selecting the source. Tap empty canvas to exit — the mode stays armed so you can add 2, 3, 4 wires in one session.

🗑️ Deleting wires

Desktop: click a wire to select it and press Delete or Backspace. Mobile: simply double-tap any wire.

Duplicate guard. Identical duplicate wires (same source port → same target port) are politely refused, so you can never accidentally double-fire an action.

Flow nodes Triggers & Forms

Flow nodes are the skeleton of your script. A Trigger owns exactly one open output and no input — it is where execution begins. A Form receives that signal on its trigger port and exposes two further outputs: a flow output (controls / buttons) for building the form's contents, and an action output (submit / select) for what happens afterwards.

Control nodes Inputs & Elements

Controls chain off the form's content port. Each has one in and one next, so the wire order is the render order. Every value-producing control (Toggle, Slider, Dropdown, Search, Text Input) exposes a Result name in Properties — that becomes a const in the generated script and is what you reference as ${name} inside conditions and commands.

Only those value-producing controls occupy a slot in res.formValues. Label, Header and Divider are display-only, so the generated script indexes formValues[0], [1], [2]… straight through the inputs in chain order, skipping them.

† Why these three have no builder call. The stable @minecraft/server-ui 1.x ModalFormData exposes exactly seven methods — dropdown, show, slider, submitButton, textField, title and toggle. There is no .label() in the stable API, so Label, Header and Divider are emitted as text lines inside the form's .body(). They appear in the preview in chain order, but they do not consume an index in res.formValues — only Toggle, Slider, Dropdown and Text Input / Search do.

Button labels on a Message form. MessageFormData in 1.x exposes only body, show and title — there is no .button() method, so the confirm and cancel captions cannot be renamed from a stable-API script. Branch on res.selection (0 = confirm, 1 = cancel) instead.

API version. This manual documents the editor's output target — the stable @minecraft/server-ui 1.x line (1.0.0 → 1.3.0), positional arguments only. A newer 2.x stable line now exists on npm; signatures there may differ, so pin "version": "1.x" in your pack manifest to match the generated code.

Action nodes Commands & Execution

Actions are the leaves of the tree. Most are linear (in → next) and run top to bottom. Condition is the only branching node: it evaluates left <op> right after ${result} interpolation and sends execution down yes ✓ or no ✗. Open Form is the only action that leaves the current form and enters another one.

Interpolation. Anywhere you can type text — messages, commands, titles — you can reference a control's result with ${resultName}. The generator emits a real template literal, so tp @s ~ ${targetY} ~ becomes `tp @s ~ ${targetY} ~` in the output.

Interactive Live Preview & Game Output

#

The bottom bar is split in two and always reflects the currently selected trigger path. The left pane is a pixel-accurate Bedrock form simulator — real grey chrome, bevelled buttons, working toggles, sliders and text fields. The right pane is an event trace that logs exactly what the generated script would do at runtime.

What the simulator renders

  • Form title with § colour codes honoured
  • Body text, labels, headers and dividers in chain order
  • Buttons (with icon textures when you attached images)
  • Toggles, sliders, dropdowns, text and search fields — all interactive
  • Submit / cancel buttons, matching your configured labels

What Game Output logs

  • Which trigger fired, and the item / entity / command that fired it
  • The submitted formValues mapped to your result names
  • Every command string after ${var} substitution
  • Condition evaluations — which branch was taken and why
  • Effects granted, sounds played, teleports and page navigations

Why this matters

The single most common bug in hand-written Script UI code is an off-by-one index into res.formValues. Because the simulator uses the exact same chain the generator walks, a flow that behaves correctly in the preview produces correct indices in the export. If the preview is wrong, the code is wrong — and you find out before Minecraft does.

Cancellation. Pressing Cancel (or closing the form) sets res.canceled; the generated script returns early, so none of your actions run. The preview console prints the cancellation so you can confirm the guard works.

Multi-Page Navigation (Open Form Node)

#

Real menus are rarely one screen. The 📂 Open Form action node turns any button into a redirect to another form — the same pattern as a main menu opening a sub-menu.

How to wire a page

  1. Build your destination form first (its own Trigger is optional — pages opened by a button don't need one).
  2. On your menu form, add a Button control and label it (e.g. ⚙️ Server Settings).
  3. From the button's on click port, wire an Open Form node.
  4. In Properties, pick the Target form. The dropdown lists every form in the project.
  5. Repeat for each menu entry — one trigger, many pages.
typescriptgenerated · page navigation 
function openForm_mainMenu(player) {
  const menu = new ActionFormData()
    .title("§l§6Server Menu")
    .button("⚙️ Server Settings")
    .button("🧭 Teleports");

  menu.show(player).then((res) => {
    if (res.canceled) return;
    if (res.selection === 0) openForm_serverSettings(player);  // Open Form →
    if (res.selection === 1) openForm_teleports(player);
  });
}

In the Live Preview

Pressing a button wired to Open Form switches the simulator to that page instead of running actions — so you can click through the whole menu tree. When the project has multiple forms, a page picker appears above the preview so you can jump straight to any page.

In the exported script

Each form becomes its own function openForm_<name>(player), and Open Form compiles to a direct call to the target function — no string lookups, no runtime registry, nothing to fall out of sync.

Avoid cycles. Page A → Page B → Page A is legal but will re-open forms forever if the player keeps clicking. Add a “⬅ Back” button that opens the parent page rather than chaining deeper, and keep nesting to two or three levels.

Installing and Running in Minecraft Bedrock

#

Option A — the .mcaddon (fastest)

  1. Download YourProject.mcaddon from the Generate window.
  2. Double-click / open the file — Minecraft imports it and shows both packs in your library.
  3. Create or edit a world → Behavior Packs → activate your pack. The resource pack is pulled in automatically by the dependency.
  4. In the same world settings, scroll to Experiments and switch on Beta APIs.
  5. Play. Hold the trigger item (e.g. minecraft:compass) and crouch-use it to open your menu.

Option B — copy into an existing pack

  1. Press 📋 Copy JavaScript (or TypeScript, then compile it yourself).
  2. Paste it into behavior_pack/scripts/main.js.
  3. Make sure the pack's manifest.json declares a script module with entry pointing at scripts/main.js, plus dependencies on @minecraft/server and @minecraft/server-ui.
  4. Enable Beta APIs in the world's Experiments and reload the world.

Troubleshooting & Best Practices

#

Common problems

My form never opens in-game

Check, in order: (1) Beta APIs is enabled in the world's Experiments; (2) the behaviour pack is activated for that world, not just imported; (3) the trigger's Item ID matches exactly, including the minecraft: namespace; (4) if the trigger is a crouch variant, you are actually sneaking when you use the item. The Live Preview always fires the flow, so if it works there the wiring is fine and the problem is in the world setup.

Scripts error with “module not found”

Your manifest.json must declare dependencies on both @minecraft/server and @minecraft/server-ui, and the modules[].entry must point at scripts/main.js. If you exported TypeScript, compile it to JS first — Bedrock does not run .ts.

Button icons show as missing / pink-black

Icons live in the resource pack. Export a .mcaddon so the RP is bundled and the BP→RP dependency is written for you, and make sure the RP is active in the world. Textures must be .png.

Wrong values after submit (off-by-one)

res.formValues is indexed in chain order. Reordering controls on the canvas changes the indices. Re-run the Live Preview after any reorder — the Game Output prints each result name next to its value so you can confirm the mapping.

I can’t drag from the palette on my phone

Mobile browsers don't fire HTML5 drag events, so the editor uses a touch ghost-drag that follows your finger. If it still misbehaves, just tap the palette item — it drops at the canvas centre and you can drag it into place afterwards.

My project disappeared

Browser-storage projects live in localStorage, which is cleared when you wipe site data or use a private window. Export a .dcui regularly, or choose Device / internal folder storage when creating the project.

The public live URL stopped working

GitHub Pages cannot serve a private repository on the free plan. Either make the repository public again, or run locally with python3 -m http.server 8080 and open http://localhost:8080.

Best practices

🧱 One trigger, one job

Split unrelated menus into separate triggers and forms instead of one giant modal. It keeps formValues indices stable and the canvas readable.

🏷️ Name every result

Set explicit Result names on inputs. ${targetY} is self-documenting in commands; formValues[3] is not.

📝 Document with notes

Sticky notes travel with the project file — use them to record why a condition exists, not just what it does.

▶ Preview before export

Every flow should be exercised once in the simulator, including the cancel path and both condition branches.

🧭 Keep menus shallow

Two or three levels of Open Form pages is plenty. Add a Back button instead of chaining deeper.

💾 Export .dcui often

The project file is tiny. Keeping one next to your behaviour pack means you can regenerate after any Minecraft API change.
